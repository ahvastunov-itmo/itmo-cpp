## Конкурентность и параллелизм

В чём ключевое различие concurrency и parallelism?

::: {.quiz-options}
1. Это всегда одно и то же.
2. Конкурентные задачи могут чередоваться на одном ядре; параллелизм означает одновременное выполнение.
3. Конкурентность бывает только на четырёх ядрах.
4. Параллелизм запрещает несколько задач.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Конкурентность не требует физической одновременности.** Параллельное выполнение — один из способов исполнять конкурентные задачи.

[Повторить: Concurrency vs Parallelism](../lectures/22-concurrency.md#concurrency-vs-parallelism){target="_blank"}

</details>

## Закон Амдала

20% работы строго последовательны, 80% идеально распараллеливаются. Каков предел ускорения при неограниченном числе исполнителей без накладных расходов?

::: {.quiz-options}
1. В `80` раз.
2. Ускорение не ограничено.
3. В `5` раз.
4. В `20` раз.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Предел равен `1 / 0.2 = 5`.** Последовательная доля остаётся даже при идеальном ускорении параллельной части.

[Повторить: Закон Амдала](../lectures/22-concurrency.md#закон-амдала){target="_blank"}

</details>

## join

Что делает `join()` для joinable-потока?

::: {.quiz-options}
1. Ожидает завершения связанного потока.
2. Отделяет его и немедленно забывает.
3. Насильно прерывает его в текущей инструкции.
4. Только меняет его имя.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Ожидает завершения.** После успешного `join()` объект потока больше не является joinable.

[Повторить: std::thread](../lectures/22-concurrency.md#stdthread){target="_blank"}

</details>

## Деструктор thread

`std::thread` уничтожается, пока `joinable()` возвращает `true`. Что предусмотрено стандартом?

::: {.quiz-options}
1. Вызов `std::terminate`.
2. Автоматический `join()`.
3. Гарантированное игнорирование.
4. Автоматический `detach()`.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Вызывается `std::terminate`.** Завершение работы самой функции потока ещё не заменяет `join()`; жизненным циклом объекта `std::thread` нужно управлять.

[Повторить: std::thread](../lectures/22-concurrency.md#stdthread){target="_blank"}

</details>

## Гонка данных

Два потока без синхронизации увеличивают один обычный `int`, переполнение исключено. Как оценить программу?

::: {.quiz-options}
1. Гонка данных ведёт к неопределённому поведению.
2. Результат всегда точен.
3. Только одно приращение иногда теряется, остальные гарантии сохраняются.
4. Компилятор обязан сделать операции атомарными.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Это неопределённое поведение из-за data race.** Нельзя описывать его лишь как «иногда неверный счётчик»; вопрос анализирует ошибку, а не предлагает запускать её.

[Повторить: Race Condition](../lectures/22-concurrency.md#race-condition){target="_blank"}

</details>

## lock_guard

Зачем использовать `std::lock_guard<std::mutex>`?

::: {.quiz-options}
1. Чтобы связывать удержание мьютекса со временем жизни RAII-объекта.
2. Чтобы запретить все исключения.
3. Чтобы сделать несколько потоков одним процессом.
4. Чтобы автоматически защищать любые данные без использования того же мьютекса.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Блокировка освобождается в деструкторе.** Для защиты данных все конфликтующие обращения должны соблюдать одну согласованную схему синхронизации.

[Повторить: std::mutex](../lectures/22-concurrency.md#stdmutex){target="_blank"}

</details>

## Атомарное приращение

Потоки должны увеличивать общий `std::atomic<int>` без потери приращений. Какую операцию выбрать при отсутствии переполнения?

::: {.quiz-options}
1. Обычное присваивание соседней переменной.
2. Раздельные `load()`, вычисление и `store()` без дополнительной защиты.
3. Только `volatile int`.
4. `fetch_add(1)` как единую read-modify-write операцию.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**`fetch_add` атомарно объединяет чтение и изменение.** Раздельные атомарные `load` и `store` не делают всю последовательность одной атомарной операцией.

[Повторить: std::atomic](../lectures/22-concurrency.md#stdatomic){target="_blank"}

</details>

## Порядок блокировок

Два потока захватывают два мьютекса в противоположном порядке. Какой риск появляется?

::: {.quiz-options}
1. Автоматическое ускорение обоих потоков.
2. Взаимная блокировка, когда каждый ждёт ресурс другого.
3. Гарантированное завершение одного потока.
4. Обязательная ошибка компиляции.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Возможен deadlock.** Согласованный порядок захвата или подходящий механизм совместного захвата помогает избежать такой циклической зависимости.

[Повторить: DeadLock](../lectures/22-concurrency.md#deadlock){target="_blank"}

</details>

## Условная переменная

Почему ожидание `condition_variable` связывают с проверяемым под мьютексом предикатом?

::: {.quiz-options}
1. Потому что `notify_one` навсегда запоминает событие.
2. Чтобы заменить данные одним уведомлением.
3. Из-за ложных пробуждений и необходимости проверять фактическое состояние данных.
4. Чтобы разрешить одновременную запись без синхронизации.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Предикат определяет, можно ли продолжать работу.** Само пробуждение не доказывает, что условие выполнено; после него состояние нужно проверять снова.

[Повторить: std::condition_variable](../lectures/22-concurrency.md#stdcondition_variable){target="_blank"}

</details>

## promise и future

Как обычно связаны `std::promise<T>` и полученный из него `std::future<T>`?

::: {.quiz-options}
1. Оба всегда создают отдельный поток.
2. `future` сам вычисляет любое значение без производителя.
3. `promise` публикует значение или исключение, `future` позволяет дождаться и получить результат.
4. Они предназначены только для блокировки мьютекса.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Они разделяют состояние результата.** Производитель устанавливает значение или исключение, а потребитель получает его через `future`.

[Повторить: std::future and std::promise](../lectures/22-concurrency.md#stdfuture-and-stdpromise){target="_blank"}

</details>
