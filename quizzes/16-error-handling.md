## assert и ввод

Почему `assert` не подходит как единственная проверка некорректного пользовательского ввода?

::: {.quiz-options}
1. Работает только в многопоточных программах.
2. Он всегда выбрасывает `std::exception`.
3. Проверки могут отключаться при определённом `NDEBUG`.
4. Он всегда исправляет ввод.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**`assert` может быть отключён.** Для ожидаемых ошибок внешних данных нужна обычная логика обработки, которая остаётся в рабочей сборке.

[Повторить: Assert](../lectures/16-error-handling.md#assert){target="_blank"}

</details>

## Перехват по ссылке

Почему полиморфные исключения обычно перехватывают по `const`-ссылке?

::: {.quiz-options}
1. Чтобы избежать лишнего копирования и срезки объекта исключения.
2. Чтобы исключение стало глобальной переменной.
3. Чтобы всегда изменить тип исключения.

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Ссылка сохраняет исходный объект исключения.** Перехват базового типа по значению может срезать производную часть.

[Повторить: std::exception](../lectures/16-error-handling.md#stdexception){target="_blank"}

## Раскрутка стека

При выходе из области видимости из-за исключения к найденному обработчику что происходит с полностью сконструированными локальными объектами?

::: {.quiz-options}
1. Все остаются жить до завершения программы.
2. Они все копируются в обработчик.
3. Удаляются только указатели, без вызова деструкторов.
4. Вызываются их деструкторы.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Локальные объекты уничтожаются при раскрутке стека.** Благодаря этому RAII освобождает связанные ресурсы.

[Повторить: Stack unwinding](../lectures/16-error-handling.md#stack-unwinding){target="_blank"}

</details>

## Базовая гарантия

Что обещает basic exception guarantee?

::: {.quiz-options}
1. Объект обязательно побайтово не изменился.
2. Инварианты сохранены и ресурсы не утекли, но состояние могло измениться.
3. После ошибки объект можно только забыть.
4. Исключений никогда нет.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Состояние остаётся корректным, утечек нет.** Возврат к прежнему состоянию — уже более сильное обещание.

[Повторить: Гарантии безопасности исключений](../lectures/16-error-handling.md#гарантии-безопасности-исключений){target="_blank"}

</details>

## Сильная гарантия

Что добавляет strong exception guarantee?

::: {.quiz-options}
1. Любая ошибка автоматически игнорируется.
2. Компилятор запрещает все `throw`.
3. Ресурсы можно освобождать позже вручную.
4. При неудаче операция не меняет наблюдаемое состояние, которое обещает защитить.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Неудачная операция не оставляет изменений защищаемого состояния.** Часто результат готовят отдельно, а затем фиксируют невыбрасывающим обменом.

[Повторить: Strong guarantee](../lectures/16-error-handling.md#strong-guarantee){target="_blank"}

</details>

## noexcept

Что произойдёт, если исключение покидает функцию, объявленную `noexcept`?

::: {.quiz-options}
1. Будет вызван `std::terminate`.
2. Всегда вернётся нулевой результат.
3. Компилятор задним числом удалит вызов.
4. Оно молча исчезнет.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Вызывается `std::terminate`.** Внутри функции можно бросить и перехватить исключение; запрещён именно выход исключения наружу.

[Повторить: noexcept](../lectures/16-error-handling.md#noexcept){target="_blank"}

</details>

## Второе исключение

Из деструктора при раскрутке стека выходит ещё одно исключение. К чему это приводит?

::: {.quiz-options}
1. Оба всегда попадают в один `catch`.
2. К `std::terminate`.
3. Раскрутка стека приостанавливается до следующего вызова.
4. Первое исключение автоматически заменяется вторым.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Программа вызывает `std::terminate`.** Освобождение ресурсов в деструкторах должно быть организовано так, чтобы исключения не выходили наружу.

[Повторить: Stack unwinding](../lectures/16-error-handling.md#stack-unwinding){target="_blank"}

</details>

## Код возврата

Какое обязательство появляется у вызывающего кода при передаче ошибки кодом возврата?

::: {.quiz-options}
1. Удалить все обработчики.
2. Всегда завершать процесс даже при успехе.
3. Никогда не проверять результат.
4. Проверить результат и обработать ошибку по контракту функции.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**Нужно проверить и обработать результат.** Сам возврат кода не заставляет вызывающий код заметить ошибку.

[Повторить: Код возврата](../lectures/16-error-handling.md#код-возврата){target="_blank"}

</details>

## expected и версия языка

В лекции показан `std::expected<T, E>`. Какое утверждение корректно?

::: {.quiz-options}
1. Оно всегда хранит одновременно успешное значение и ошибку.
2. Оно входит в C++98.
3. Это средство C++23 для значения или ошибки, не часть стандартной библиотеки C++20.
4. Оно запрещает проверять наличие ошибки.
:::

<details class="quiz-explanation">
<summary>Ответ и объяснение</summary>

**`std::expected` добавлен в C++23.** Он представляет успешное значение либо ошибку; этот вопрос явно выходит за основной режим C++20.

[Повторить: std::expected (C++23)](../lectures/16-error-handling.md#stdexpected-c23){target="_blank"}

</details>
